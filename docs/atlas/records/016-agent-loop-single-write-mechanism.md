# 写入库的唯一机制是一个 agent 循环：抽取与合并合一，MergePlan 作废

抽取与合并原本是两次调用：第一次在不知道库里已有什么的前提下产出条目，第二次拿候选集回头对账。**去重这个问题是这个拆分制造出来的。** 合成一个带工具的循环之后它不再存在——context 里已有「组会材料（机器学习）」，来了「组会 PPT 明天交」，模型发一次 `updateItem` 即可，不需要相似度阈值。

**MergePlan 契约作废**，合并成为循环内的一次 `updateItem`。这是三份已冻契约中唯一被推翻的一份。

**触发它的是碎片，不是 prompt。** 输入面就是已有的四个采集入口，没有第五个。用户输入的指令与用户投放的材料同口，不分流：是材料就 `createItem`，是指令就 `updateItem`，由模型在同一次循环里判断，因此不存在误路由这种失败。「把组会挪到周四」本身就是一条 text 碎片，不可变、永不删除；由它引发的变更引用它，改期因此也有出处。

**Context 优先，工具兜底。** 恒定给出当前日期时刻、时区、学期与校历、全部项目；条目清单给未完成的全部加最近 14 天，每条只给标识、类型、标题、时间、所属项目。装不下时按时间窗切，**不按相关性预筛**——预筛要先知道什么算相关，而那正是未知的。**切了必须在 context 内写明范围与窗外条数**，否则模型不知道自己没看见什么：碎片讲三个月后的事，它在窗口内找不到已有条目就会新建一条重复的，且不会想到去检索。窗口边界必须是它看得见的事实，不能是一个它意识不到的缺口。

工具六个。读：`getItem`、`searchItems`、`getProject`。写：`createItem`、`updateItem`、`dropItem`（标记丢弃，不是删除）。**没有 `createProject`**——建项目是 `createItem` 的 `project` 参数（三选一带引文，见 [[010-project-layer-above-items]]）在同一次工具执行内的副作用，拆成两个工具会产生「项目已建、条目未归入」的中间态。

[[007-extraction-contract]] 里只有一句不再成立：那份 zod schema 不再是发给 API 的 `response_format`，而是 `createItem` 的参数 schema。严格模式、类型、逐字引用校验、RRULE、零条目是正常结果、结构化来源不走这条契约，全部原样。该记录末句提到的「去重合并那一段共用」已不存在——结构化来源改由 `store/upsertByExternalId` 按主键写入，不经过循环。

**校验位置的变化是净收益。** 原先整批产出后校验，一个字段引错则整次调用作废；现在校验在工具执行那一刻进行，不通过就把错误作为工具结果返回让模型改。

**步数上限 8，超出即大声失败**，已落库的写入不回滚——它们各自有效，回滚会抹掉用户已经看见的条目。重试安全，因为那几条已在 context 的条目清单内，模型看得见，不会重建。

**置信度换了来源**：不再是字面重合度，也不是让模型自报把握；模型照常给 `confidence`，但它不再自动决定进不进待确认——低置信度直接落库，用户改一下就行。仍分不清是否同一条时默认不合并，而不是塞进 `needs_confirm`。当前唯一由创建路径进待确认的是「进度没有所属项目」，见 [[015-needs-confirm-threshold]]。

**只读的不走循环。**「此刻」与「更小的一步」一次调用产出结果，不带工具。分界是：**要改库的走带工具的循环，只读的走一次生成。** 让「此刻」自己决定看什么，恰好会推翻 [[013-context-is-a-query]] 从模型手里拿走的那件事。
