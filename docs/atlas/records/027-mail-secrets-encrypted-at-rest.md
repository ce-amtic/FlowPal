# 邮箱授权码密文入库、明文只在内存，账号是库里的数据不是配置

门户那条路一行密码都不存（[[026-school-auth-is-a-real-login-window]]），邮箱做不到
——IMAP 没有别的凭据形式。原先把它放在 `config.local.json` 里，等于「唯一存密码的
地方」既是明文、又只能有一份、还改不了。三条都不成立了：用户要在设置页上随时增删
改，而且学校邮箱和私人邮箱是两个。

于是分成三处存，各存一样：

- **钥匙**在系统钥匙串里（Electron `safeStorage`）。
- **密文**在 `mail_accounts` 表里，跟条目、碎片同一个 `.db` 文件。
- **明文**只在 server 进程的内存里，由桌面端启动时解一次密推进来。

**这条边界的形状是被「server 不依赖 Electron」逼出来的，不是选出来的。** server 拿
不到钥匙串，所以它解不开自己库里那一列——它只能搬运密文，等桌面端把明文送来。代价
写在明处：`pnpm dev:server` 单跑时没有明文，邮箱那几路显示「需要在桌面应用里解锁」。
那句话是对的，那台进程上确实没有钥匙。

换来的是一句可以说出口的话：**拿到 `flowpal.db` 不等于拿到授权码。**

两个随之而来的规矩：

- **钥匙串不可用时抛错，不退回明文存盘。** 用户看见「已加密」是因为我们说了；悄悄
  降级等于说了谎。
- **「没解锁」与「授权码不对」在界面上必须是两句话。** 前者重开一次应用就好，后者
  要去邮箱设置里重新生成一串。混成一句「不可用」，用户会去改对的那一半。

协议选 IMAP 不选 POP3，理由不在协议在产品：POP3 拿不到 `\Seen`，而「只读你还没处理
过的、不替你标已读」这条完全建立在服务端的已读标记上。换成 POP3 就只能靠自己的水位
猜，结果是昨晚已经读完并处理掉的邮件明早又被喂一遍模型。
