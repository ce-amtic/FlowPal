# 学校系统的鉴权是一次真人登录加 Cookie 搬运，程序不碰密码

骨架当初假设教务凭据是配置里的一对学号密码（`config.ruc`），由程序自己去登录。
这条走不通，而且不是「难」而是「不该」：CAS 的登录页上同时挂着图形验证码、短信
验证码、人脸，密码还在前端加过一道；无头重放那套表单是在猜一个随时会变的东西，
猜错的代价是真实账号被锁。既有的 Flutter/Dart 实现早就是这么定的，理由写在它的
会话层第一行——**本程序不接触密码**。

所以：用户在桌面端开的一个真浏览器窗口里登录一次，那次登录留下的 Cookie 被搬到
server 的罐子里，之后所有取数由 server 自己发出。`config.ruc` 那个字段随之删除。

两条随之而来的结构性后果：

- **server 仍然不知道浏览器存在。** 它只认一批 Cookie，入口是
  `POST /api/sync/session`；开窗口、采 Cookie 是桌面端的事。这跟「业务逻辑不依赖
  Electron」是同一条边界，没有为同步破例。
- **「需要重新登录」多数时候不需要用户输密码。** 票据授予 Cookie 活得久，缺的往往
  只是一份没过期的子系统会话，重新采集一遍就好。所以失效是一个**状态**而不是一句
  错误：设置页显示它，桌宠不为它弹东西。

唯一存密码的地方是学校邮箱，因为 IMAP 没有别的凭据形式；那一段是显式配置，不配
就整条来源不跑。

取数走门户的日程中心而不是直连教务：**一个接口同时给课表、校历和用户自己的日历**，
而且调课只在这里看得见——教务那边的周次位图是排课时定死的，学校把某个周日定成
「上星期二的课」时位图不会变。代价是形状由门户说了算，验收因此分成两半：不联网的
那一半验解析与落库（`pnpm check:sync`），联网的那一半验接口今天还在不在
（`pnpm sync:once`）。
