# 投放的响应形状按「经不经模型」分成两种

`POST /api/fragments` 有两种收场，由这条碎片要不要经过模型决定：

- **经模型**（文字、图片）：`202`，只带 `{ fragment, run }`，循环在后台跑。调用方拿
  `run.id` 订阅 `/api/runs/:id/events` 才看得见这几十秒里它在动哪一样东西；条目由
  「变了」那条广播让各页自己重取。
- **不经模型**（同步来的课表、拖进来的 ICS）：`200`，带 `{ fragment, run, items }`，
  当场就跑完了。解析加入库是几毫秒的事，中间没有任何值得播的进展。

这不是两套接口，是同一个接口对两种耗时的诚实交代：状态码本身说明了这次是「收下了，
还在做」还是「做完了」。

之前两边各按一种假设写：进度那条流要求立刻拿到 run.id，而 ICS 的断言要求响应回来时
条目已经在库里。全做成异步，桌宠的回执会永远显示 running；全做成同步，回复区那一行
就只能显示一句「正在理解」。

代价是调用方得知道 `items` 只在同步那一路有——所以它在类型上是可省的，而不是一个
永远存在、有时为空的数组。空数组会让「没抽到东西」和「还没跑完」看起来一样。

要在回执里交代结果的调用点（桌宠、快捷键）用 `api.awaitRun(runId)` 等那条流的终局，
不自己轮询。相关：[[017-agent-output-is-receipt]]、[[023-run-summary-survives-the-run]]。
