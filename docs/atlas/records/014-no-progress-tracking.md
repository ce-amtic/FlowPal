# 不做进度追踪：收缩成完成状态与「多久没动」

进度追踪是结构性不可解的，不是做不完。

活儿发生在我们看不见的地方——文档里、书上、纸上。要看见就得监控，而监控是非目标；剩下的只有自陈，而自陈在「刚结束专注、想赶紧关掉界面」的时刻质量最差。**换问法解决不了：问题不在问法，在于那个时刻的人没有动机给准确答案。**

可靠来源只有三个，全部是副产品：

- 用户自己扔进来的进度陈述——他说出来是为了卸载，不是为了汇报，动机对所以内容真；
- 事务被标记完成——他本来就要做这个动作，而且确实知道自己做完没有；
- 一件事消耗了几次专注、跨了多少天——算出来的，不需要任何人回答。

**专注结束不问填空题。** 结束这个动作本身就是信号：「已完成 ｜ 下次继续」两个按钮，零打字。「下次继续」直接改变下一次「此刻」，用户看到的是回报不是问卷。「这件事卡住了」是算出来的，不需要自陈。

项目页里因此不是进度条，是这件事可靠已知的部分：接下来的节点、未完成、已完成、用户说过的话，以及**「多久没动」**——它测的是回避而非进展，而回避正是这道题的靶心。

真正的进度百分比只有一条结构性解法：把任务拆成可勾选的步骤。那会把产品变成任务管理器，且拆解质量取决于模型对一件它看不见的事的猜测，拆错了比没有更糟。

同一个结构性限制也约束「更小的一步」：模型看不见任务内容，所以它不拆任务。有材料时（条目原文，或它所属项目里的其他条目与用户说过的话）从材料里取并带引用；没有材料时降低承诺而非分解任务——更短的时间、更浅的深度、只做准备动作。没有引用又不是降承诺的具体步骤一律禁止输出。项目层（[[010-project-layer-above-items]]）因此不只是分类：攒得越多，这一步越具体。
