# 产品形态、主窗口与实现机制

## Intent

骨架已经立起来了：进程形态、三份契约、存储 schema、一条能跑通的采集链路。剩下没定的正是当初刻意推迟的那一半——这个 App 到底怎么用、主窗口长什么样、桌面上那个形象与主窗口如何分工，以及每一项能力究竟由什么机制实现。冻结在 2026-09-06 12:30，三个人。形态与机制不定，三个人没法并行：界面那个人无页可写，桌宠那个人不知道自己在做入口还是做主角，语义层那个人不知道模型该被喂什么。

本文件的唯一依据是 PROJECT.md 那句定位：**让开始变容易，让专注变自然**。既有设计文档的词汇——画像、再评估引擎、执行意向——不在此处使用：那份文档提供理论参考，不提供形态。下面的结论从那句定位与真实使用时刻推出。

## Spec

### 两个表面，分量相等

桌面上常驻一个形象，主窗口是一个完整的应用。两者分量相等，靠一条规矩保证：

**桌宠的能力是 App 能力的子集，但交互形式可以是它独有的。**

- 没有任何能力只存在于桌宠。它能做的每件事，主窗口里都有一个不着急的等价版本；桌宠不启动，App 功能完整。
- 交互形式可以独有。把桌宠抱起来拖到某个窗口上完成一次采集，是只有这个形态做得出的动作。
- 它不主动猜用户在干什么。气泡只出现在两种时候：用户刚对它做了一个动作（回执），或到了用户自己设定过的时刻。后台同步失败之类的事不弹。
- 它说的每句判断旁边都有一个否定入口。

理由是两类已知失败：Microsoft Bob 的病根是角色成了必经之路；Clippy 的病根是主动打断且不可反驳。

### 表示：项目层

本次工作要求的表示，类型是 **schema**——数据会按这个形状堆积，且活得比任何一版界面都久。

五类条目全是原子，但学生实际追踪的对象不是原子，是「实习申请」「高等数学这门课」「那篇论文」。缺这一层，长期追踪没有落脚点，进度记录也只能错误地挂在某一条事务上。

```sql
projects(id, name, status_note, status, created_at, updated_at)
  -- status: active|done|dropped

items 增加两列
  project_id  REFERENCES projects(id)   -- 可为空，多数条目为空是正常的
  external_id TEXT UNIQUE               -- 结构化来源（课表、考试、系统日历）的稳定标识
```

**归属必须指得出出处，指不出就不归。** 抽取的输出里项目归属是三选一，前两种都要带一句逐字引文：

```
{ kind: 'existing', projectId, quote }
{ kind: 'new', name, quote }
{ kind: 'none' }
```

`quote` 必须逐字出现在碎片原文里，与条目字段的引用共用同一段校验。这一条同时管住两头：不能凭氛围归类，也不能凭氛围建项目——原文里得出现一个可命名的长期事项才建。

**`new` 的名字撞上已有项目就降级成 `existing`**（忽略大小写与空白）。模型看不见的那一刻很常见——教务同步刚建了「高等数学」，模型这次输出 `{kind:'new', name:'高等数学'}`。不管这一条，同步落地的第一天项目页就会出现成对的重复项，用户会读成这一层坏了。

**项目的三个来源：**

1. **课程自动成为项目。** 教务同步一接上，每门课就是一个项目。学生的绝大部分事务属于某门课，冷启动问题因此由真实数据解决。
2. **模型直接建，不问用户。** 有引文支撑就建，不进待确认——见下面待确认的门槛。
3. **用户手动建或改归属。** 唯一需要人介入的地方是改归错的那一条，而那是随手的事。

**「未归类」是正常状态，不是待办。** 它是项目页顶部的一组，产品不催。

**进度挂在项目上**，不挂在单条事务上。项目不是文件夹：同一条既有截止日又属于项目的事务，在日程与项目两处都出现。

**进度类条目必须有所属项目。** 模型抽出进度却给不出归属时，该条以 `needs_confirm` 落库，问题是「这属于哪个项目」。

这层现在加是对的：库里还没有真实数据，加一张表和两个可空列是纯追加；有了数据再加就是迁移。

### 待确认的门槛

**进待确认的条件是「错了代价高或不可逆」，不是「模型没把握」。**

- 合并两条 → 进。合错了两件事永久并成一件，用户拆不回来。
- 低置信度的抽取结果 → 进。烂数据落进库会污染后面每一次判断。
- 项目归属 → 不进。归错点一下就改过来了。

待确认不是页面，是状态：全局一个数字，只在有内容时出现，点开是逐条确认的浮层，确认完自己消失。

### 处境：一个查询，不是一份存储

「处境」是 A 手里的一个纯函数 `buildContext(ctx)`，不是一张表、不是一份画像文档、不是向量库。

排掉的两条路：**自然语言画像文档**会漂、会编，且一旦重写就丢了来源，用户没法问「你凭什么这么说」——这直接违反「每一条都可见、可改、来源可追溯」；**向量检索**在几百条条目的量级上是纯负担。

库本身就是记忆。判断一条事实是否属于处境，用一把尺子：**它会改变产品说什么、挑哪一件，才算；把它拿掉输出不变，它就是装饰。**

`buildContext` 的输出按**来源**分节，每节标明来源，prompt 据此知道哪些能断言、哪些必须留余地。来源标签替代了画像文档该干的活。

**一、算出来的**（库里已有，现查现算）

- 每条离截止多久，是硬节点还是用户自定
- 这个窗口里同时压着几件、跨几个项目
- 哪件被改期过几次、是被哪条通知推的（`item_history` 带 `fragment_id`）
- 哪个项目多久没有任何动静

**二、观察到的**（只能来自专注时段，且只用无条件产生的四个数）

开始时刻、计划时长、实际时长、是否提前结束。

**明确排除「这段里扔了几条想法」一类指标**：它依赖用户是否使用某个可选功能，缺席时是歧义的（没杂念，和没用这个功能，是同一个空值）。在歧义的空值上做推断得到的是噪声。**规矩是只用行为本身必然产生的信号。**

**三、用户说的**（存成「状态」条目，可见可删）

不主动问。用户自己扔进来时管道会抽成一条状态，这是自然发生的。

**四、先验**（无数据，必须标明是猜的）

**明确排除的：** 情绪与性格标签（推不出来，写出来就是模型下评语，与在场而不评判冲突）；屏幕使用与 App 使用记录（非目标）；任何用户没说过也没做过的事。

**一个不粉饰的矛盾：** 题面写的是「长期」，长期意味着趋势，而到冻结时库里只有几小时的数据。演示里任何一句「长期」的话，来源要么是预置数据，要么是先验。库即记忆这条路的价值恰在于此——模型只能说出行里有的东西，说不出趋势时它就说不出，不会编一个。

### 精力：给事实，不给数

不把精力建模成一个值再交给模型。任何数值——0.63 也好、三档也好——都是从几条事实里挤出来的，挤的过程中信息只会丢：模型看到 0.63 反而不知道它从哪来，而且每次调用对它的理解不一致。

**给事实，判断交给模型。**

```
【身体与日程】
  工作日 7:20 起，休息日 10:40 起 —— 偏晚型
  计划入睡 23:30
  今天 8:00–11:50 连上四节，中间无空档
  现在 14:05，距起床 6 小时 45 分
  今天已完成 1 次专注：12:40 起，45 分钟，完成
  （专注记录共 3 次，不足以看出规律）
```

模型对「连上四节课之后」「醒后将近七小时」「偏晚型的人晚上九点」有真实的世界知识，比手搓的规则表强；可解释性直接变成免费的——用户问「你凭什么」，答案就是这几行事实。

**曲线的四层来源**，只有第四层需要历史数据：

1. **先验形状**：昼夜节律的标准形状加约 90 分钟超日节律。文献里的形状，不是我们编的。
2. **个人化参数**：MCTQ 短式两问——工作日几点起、休息日几点起——算出 chronotype，把先验整体平移。**放在首次启动，和模型 key、教务账号一起问一次。** 必须在第一次「此刻」之前拿到，第一印象只有一次。
3. **当日修正，来自课表**。这是最强的一层：今天上了几节课、什么时候上的，比体质更能决定今天的精力分布，而且第一天就有、完全个人化、可解释。
4. **观察修正**：专注完成率按时段聚合。**数据不足时不参与计算**，界面写「还在学」——三次专注算出的偏移是噪声，让它参与计算就是把噪声当信号。

**输出侧加一个约束：** 模型的结构化输出里有一个 `energy_reading` 字段放它的判断（「上午四节连堂上到中午，现在离你的高峰还有六个小时。」），**必须引用至少一条我们给的事实**。与引用逐字可验同一套纪律。这个字段就是界面上显示的那一行，不另外生成。

### 进度：结构性不可解，收缩成完成状态与「多久没动」

活儿发生在我们看不见的地方——Word 里、书上、纸上。要看见就得监控，而监控是非目标；剩下的只有自陈，而自陈在「刚结束专注、想赶紧关掉界面」的时刻质量最差。**换问法解决不了：问题不在问法，在于那个时刻的人没有动机给准确答案。**

所以不做进度追踪。可靠来源只有三个，全部是副产品：

| 来源 | 为什么可靠 |
|---|---|
| 用户自己扔进来的进度陈述 | 他说出来是为了卸载，不是为了汇报。动机对，所以内容真 |
| 事务被标记完成 | 他本来就要做这个动作，而且确实知道自己做完没有 |
| 一件事消耗了几次专注、跨了多少天 | 算出来的，不需要任何人回答 |

**专注结束不问填空题。** 结束这个动作本身就是信号：**已完成 ｜ 下次继续**，两个按钮，零打字。「下次继续」直接改变下一次「此刻」——那件事被优先推出来，第一句就是接着上次。用户看到的是回报，不是问卷。「这件事卡住了」不需要自陈，它是算出来的：同一件事消耗了几次专注。

**真正的进度百分比只有一条结构性解法**：把任务拆成可勾选的步骤。那会把产品变成任务管理器，且拆解质量取决于模型对一件它看不见的事的猜测——拆错了比没有更糟。**本轮不做，这是有意的选择，不是做不完。**

项目页里因此不是进度条，是这件事**可靠已知的部分**：

```
实习申请                          7 天没动
接下来    09/09 材料截止
未完成    填收件人 · 改简历 · 要推荐信
已完成    确定投哪几家
说过的    09/02「简历那版太长了」
```

**「多久没动」是这一页的核心**，它测的是回避而非进展，而回避正是这道题的靶心。

### 主窗口：五页、一个模式、一个设置

**此刻**——第一眼不是列表，是一件事。「不知道先干哪个」正是用户卡住的原因，给他一张表等于把问题原样退回。

```
◕   晚上好。今天是第二周的周五。

┌────────────────────────────────────┐
│  填写实习申请邮件的收件人。            │
│  周三截止，还剩 2 天。本周另有高数期中  │
│  与组会材料。                        │
│                                    │
│  [ 开始 ]   换一件   更小的一步       │
└────────────────────────────────────┘

10/08 组会材料 · 10/10 实习申请 · 10/15 高数期中
现在是低谷 · 上午四节连堂
```

- 底部那条日期带不是装饰，是「剩下的没丢」的凭据。只显示一件事而不给这个凭据，用户不敢信。
- **「开始」就是进入一次专注。**「此刻」和「专注」是同一个动作的两半。（帮用户把文件与工作区打开的那个版本推后——它依赖「记住上次开过什么」，那条不可靠。）
- 「换一件」与「更小的一步」是不同语义，且都是**本地切换**：那一次调用一次性返回主推与若干备选，每个都带自己的第一步与依据，所以点击零延迟、零费用。
- 那条精力的一行来自模型的 `energy_reading`，不是我们画的曲线图——用档位画出来的线是阶梯，画成平滑曲线就又在假装是测量。

**最近**——倒序显示每一次投放，以及它抽出了什么。

```
14:20  [截图]  微信群通知
       → 高数期中  10/15 14:00 明德主楼
       → 组会改到周四
11:40  [截图]  课程表
       → 没找到需要记的东西。原文已存。
```

它存在的理由是：**每一次投放需要一个看得见的落点。** 抽出的条目会散进日程或某个项目，用户得自己去找；零条目与失败的碎片则连找都找不到。这两件事是同一个缺口。它按时间分，不是按状态分——所以想法不该进来，也不存在「暂存区」那种「迟早要落位」的义务感。

**日程**——纵向按天的轴，不是月历格子。月历给每天同样面积，而用户只关心接下来几天；十几条数据填不满格子，看起来是空的。没有内容的天直接跳过。课表这类重复项压成每天顶上一条细带，不占条目位置。

**项目**——每个项目一张卡（上面那个形状），顶部是「未归类」组。

**想法**——倒序的流。它天生既没有时间也不属于项目，且**不需要变成任何东西**——正常归宿就是待在那儿，所以它不能被塞进任何形式的待整理区。专注结束的简报里列出这段时间扔的想法，点过去就是这一页。

**专注**——是模式不是页面：有开始和结束，进去后整个窗口换一副样子，出来回到原处。

**设置**——模型配置、教务凭据、chronotype 两问、校历、同步状态与上次结果。

### 导航

五页平级，专注是动作，设置与待确认是角落控件。导航放进已经存在的那条自绘标题栏——它本来就必须存在（隐藏系统标题栏后要靠它拖窗口），窗口里只剩一条横线，没有侧栏、没有第二层工具条。

```
● ● ●    此刻  最近  日程  项目  想法        ② ⚙
```

五格是这条栏的上限，再多就排不下。按钮周围要留足可拖动的空白。最小窗口宽度从 480 提到 640。

形象在主窗口里只出现在「此刻」与「专注」。其余三页是干活的地方，放了形象它就变成装饰，而装饰会稀释它该出现时的分量。

### 设计系统

- **卡片只用于可以整体操作的对象**（「此刻」那件事、一个项目）。列表行、想法流不是卡。卡片无描边、无分割线，只有极轻的半透明底与柔和阴影，靠这个与毛玻璃底分层。纯信息的分组只有间距和标题。既不退化成纯排版，也不长成卡片墙。
- **一个强调色**，暖的低饱和（赤陶／琥珀一类），不用蓝——蓝是所有效率工具的默认色，一眼被读成「又一个待办应用」。不引入第二强调色。
- **中文排版单独调**：正文 14、辅助 12、标题 20–24、行高 ≥1.6。正文不加粗，层级靠灰度。
- **圆角与间距各一套值**：容器 12、标签 999、间距取 4 的倍数。不允许现场发明数值。
- **动效有规格**：时长三档 120／220／400ms，全 App 一条缓动曲线。元素从它该来的地方来——列表点开详情是标题原位放大，不是新页面淡入；列表重排是移动，不是重绘。用 framer-motion 的 layout 动画实现。尊重系统「减弱动态」设置。
- 深浅色跟随系统，毛玻璃底保留（均已实现）。

**这套值必须最先落地，且由界面那个人独自定。** 桌宠与主窗口共用同一套颜色、圆角、动效档位；晚定两小时，两边就各长一套。

### 界面文案

正式、清晰、简明。不口语化，不自创黑话，不啰嗦；能一句说清的不写一段；不写面向开发过程的解释性元语句。这条覆盖界面上所有字，**包括模型生成的那部分**——抽取与「此刻」的 prompt 都要带上它。

### 桌宠

形象素材沿用团队已有的一版，不重新发明。表达方式：单色几何体，靠眼睛形状、整体形变与位移表达状态，不加拟人五官。状态少而明确：待机（呼吸）／接收（压扁、眯眼）／处理中／完成／有问题／专注陪伴中。纯 SVG + CSS，不用位图、不用 Lottie。

「放在桌面上不突兀」暂记为规格，按实际形象调：极淡或无投影、贴边时降低不透明度、鼠标靠近才完全实体化、不盖在全屏应用之上、形状之外鼠标穿透。形象与其余元素的风格是否搭配留待素材进仓库后再看。

**拖桌宠到窗口上采集**是这个形态里最独特的动作。拖窗口是「搬一个重物给你」，拖桌宠是「抱它过去看一眼」，心理成本低一个量级，并且把它从图标变成一个有身体的东西。

**不让模型做视觉定位。** 给模型一张全屏图加一个坐标、指望它找出那是哪个窗口，在原生多模态模型上不稳（那是视觉定位任务，不开 thinking with images 更不稳），接了 OCR 前置的模型则完全没有可能。改由操作系统定位：

1. 松手时用 `screen.getCursorScreenPoint()` 取坐标；
2. 按前后叠放顺序遍历系统窗口列表，第一个包含该点且不是桌宠自己的窗口即目标；
3. 用该窗口的 ID 截取**只有那一个窗口**的图，作为碎片入库。

窗口列表用跨平台的现成模块（`node-window-manager` 一类）。窗口边界与所属 App 名不需要授权，窗口标题需要——只用前两者。macOS 截图需要「屏幕录制」授权，Windows 不需要。两个平台都做，Mac 优先。

**授权失败不做兜底。** 让用户自己截图再粘到主窗口，和这个功能不存在是等价的。拿不到就大声报错。

**因为截图是按窗口 ID 截的，桌宠不在照片里**，不需要先藏起来再截。

### 桌宠窗口的工程约束

**两个窗口用 Vite 多入口**，`index.html` 与 `pet.html` 两份。单入口带 `?window=pet` 会让桌宠加载主窗口那一整包（五页、路由、数据层），而桌宠必须是瞬时出现的东西。

```
transparent: true, frame: false, resizable: false,
hasShadow: false, skipTaskbar: true, alwaysOnTop: 'floating'
showInactive() 显示，不抢焦点
setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: false })
```

`transparent` 与 `vibrancy` 不能共存——桌宠没有毛玻璃，质感全靠形象本身。

**桌宠必须手动拖，不能用 `-webkit-app-region: drag`。** 系统一接管拖动，渲染进程就收不到鼠标事件，松手坐标拿不到，命中判定就没了。做法是 `mousedown` 记起点 → `mousemove` 把位移发给主进程 `setBounds` → `mouseup` 取光标坐标做命中判定。

形状之外鼠标穿透用 `setIgnoreMouseEvents(true, { forward: true })`，渲染进程在 `mousemove` 里判断指针是否落在轮廓内，进出时切换。

### 「更小的一步」

模型看不见那件事的内容。「改简历」四个字里没有可拆的东西，硬拆就会编出听着合理、纯属虚构的步骤——用户一眼看得出它在瞎猜，那是最伤的一种失败。

**它不拆任务。** 心理上起作用的不是分解，是降低承诺。模型按手上有没有材料二选一：

1. **有材料时从材料里取，且必须带引用。** 材料有两处：该条目自己的原文与引用；**它所属项目里的一切**——其他条目、已完成的、用户说过的话。「改简历」是空的，但如果它属于「实习申请」，而项目里有一条用户说过的「简历那版太长了」，那么「把第二页那段实习经历砍掉」就是有依据的。
2. **没有材料时降承诺，不拆任务。** 更短的时间（只做五分钟）、更浅的深度（只打开文件不用写）、只做准备动作（先把要交的东西找出来）。这三种不需要知道任务是什么，而且正是有效的那部分。

**禁止第三种：没有引用、又不是降承诺的具体步骤，一律不许输出。**

连带效果：项目里攒的东西越多，「更小的一步」越具体。这是**一次演示里就看得见的长期效应**，不像趋势那样需要几周数据，也让项目层不只是一个分类。

**给 A 的提醒：** 这里的「出处」和 `item_citations` 不是一回事。那张表存的是「条目的某个字段是从原文哪一段读出来的」；这里是「此刻」这次输出用了哪几条材料，是一个 `basis` 字段，列条目 ID 或碎片引文。混了会把一堆不是抽取来的东西写进 `item_citations`。

### 「此刻」的调用与缓存

- 打开「此刻」时调一次；一次返回主推与两三个备选，每个带自己的第一步与依据。
- 结果**落库**缓存（不放内存），这样桌宠气泡与主窗口看到的是同一件事，不会各说各的。
- 失效条件三选一：跨了半小时、库里有写入、用户按「重新想一个」。不失效就用上次的——**反复打开主窗口应当看到同一件事，每次都换才叫不靠谱。**
- 第一次打开要等一次模型调用，那几秒屏幕上放什么由 C 设计，不能是转圈。
- **库里没有活着的条目时不调模型**，路由直接返回空，页面显示投放入口。这是「给事实、判断交给模型」唯一没有事实可给的情况，硬调一次只会得到一件编出来的事。`pnpm demo:reset` 清成空库是合法状态，不是异常。

### 写入库的唯一机制：一个 agent 循环

抽取与合并合并成一件事，由同一个带工具的循环完成。拆成两次调用是错的：第一次被迫在不知道库里已有什么的前提下产出条目，第二次再回头对账——去重这个问题是拆分本身制造出来的。context 里若已有「组会材料（机器学习）」，来了一条「组会 PPT 明天交」，模型直接发一次 `updateItem` 即可，不存在合并这一步，也就不需要相似度阈值。

**触发它的是碎片，不是 prompt。**输入有三处，都已存在：主窗口的投放框、形象上的输入气泡与全局快捷键、抱起形象拖到某个窗口截图。**用户输入的指令与用户投放的材料走同一个口，不需要分流**——是材料就 `createItem`，是指令就 `updateItem`，这是模型在同一次循环里的判断，不是一次前置路由，因此不存在误路由这种失败。存储层同样不区分：「把组会挪到周四」就是一条 text 碎片，不可变、永不删除；由它引发的变更引用它，`item_history` 那一行指回它。改期因此也有出处，引用纪律没有例外。

**Context 优先，工具兜底。**多数情况不需要检索，该看的东西在第一次调用前就在 prompt 里。

- **恒定给出**：当前日期时刻、时区、当前学期与校历；全部项目的 `id`、`name`、`status_note`、`status`。项目在演示规模下数十个，不切。
- **条目清单**：未完成的全部，加最近 14 天内已完成或已发生的。每条只给 `id`、`type`、`title`、时间字段、`project_id`。不给原文碎片、不给引用、不给历史——那是 `getItem` 的职责。想法也在清单内，只给标题与时间：「记得回小王」与后来的「小王说下周三面试」要能对上。

**装不下时按时间窗切，不按相关性预筛。**预筛要先知道什么算相关，而那正是未知的。

**切了必须在 context 内写明切了什么：**

```
以下是 2026-08-22 至 2026-09-19 的条目，87 条。
此范围之外另有 34 条，用 searchItems 查。
```

缺这一句，模型不知道自己没看见什么。碎片讲的是三个月后的事，它在窗口内找不到已有条目就会新建一条重复的，而且不会想到去检索——它以为自己看全了。**窗口边界必须是它看得见的事实，不能是一个它意识不到的缺口。**这是大声失败在 prompt 这一层的对应物。

**工具六个。**读：`getItem(id)`（全字段与来源碎片原文）、`searchItems(query, {from, to})`（窗口之外）、`getProject(id)`（`status_note` 与该项目下全部条目）。写：`createItem`、`updateItem`、`dropItem`——`dropItem` 是标记丢弃，不是删除，碎片永不删除这条不动。

**没有 `createProject`。**建项目是 `createItem` 的 `project` 参数（前述三选一，带引文）在同一次工具执行内的副作用。拆成两个工具会产生「项目已建、条目未归入」的中间态。

**抽取的 zod schema 就是 `createItem` 的参数 schema**，一份定义同时充当 strict 工具参数、TS 类型与入库校验器。严格模式、类型、逐字引用校验一并适用。

**引用校验在工具执行那一刻进行**，不通过就把错误作为工具结果返回，让模型改这一条。一个字段引错只损失一次工具调用，不损失整批产出。

**循环步数上限 8，超出即大声失败**，不静默截断。循环没有固定步数，不设上限就会出现一次演示卡在原地。

**面向用户的那句话是循环自然结束时的文本输出，不是 `say` 工具。**一次循环建了五条也只说一句。

**合并是循环内的一次 `updateItem`。** 库里没有独立的合并阶段，也没有 MergePlan 这一层。

**置信度来自循环本身**：context 与工具都用尽仍分不清的，以 `needs_confirm` 落库。不用字面重合度，也不让模型自报把握——前者会把「数据结构作业」与「数据结构考试」判成同一件（重合度 0.67），把「组会材料」与「组会 PPT」判成两件（重合度 0.5）；后者不是凭据。合错的后果比漏合严重得多：两件事永久并成一件，用户拆不回来，所以拿不准时的默认是不合。

**「此刻」与「更小的一步」不是循环。**它们只读，一次调用产出结果，不带工具。区分是清晰的：**要改库的走带工具的循环，只读的走一次生成。**这不是维护两套东西，是同一个模型的两种用法。

**结构化来源不经过循环。**教务与系统日历走 `upsertByExternalId`，靠主键判定，见下文。

### Agent 的输出形式

三个时刻要呈现：接住了、在做、做完了。

**气泡里那句话是回执，不是结果。**结果是库变了，库变了五页跟着变。气泡负责的是「接住了、做了什么、要看的话在哪」。

气泡两行：模型那句话，其下一行动作痕迹——`新建 3 条 · 更新 1 条`，可点，点开主窗口跳到「最近」并高亮这一批。有 `needs_confirm` 的，该行换成 `1 条待确认`，点击直达该条。**不做消息流，不留历史**，数秒后自行收回。历史在「最近」页——它是 agent 全部动作的落点，这也正是那一页的定义。

**进行中播对象，不播步骤。**循环跑三步还是八步用户不需要知道，工具名更不能逐条播出——那是面向开发过程的元语句。呈现的是「在看这张截图」「在对照机器学习这门课」「在找和面试有关的条目」。

**这几句不由模型生成**，由工具调用的参数在前端本地映射：`getProject(id=3)` 映射为「在对照机器学习」，`searchItems(q="面试")` 映射为「在找和面试有关的条目」。模型没有机会编造一句好听但不真的意图，也不增加它的负担。附带效果是「它去查了项目背景」这件事被看见，而那正是这个产品该被看见的部分。

**主动说话用同一形状，但时机受限**：只在明确事件上——专注结束、同步带来一条外部改期。**不定时冒泡**，那会滑向催促。「此刻」是产品先说话的主场，它在页面上，不靠气泡。

### 采集入口

**必做四个**：主窗口打字／粘贴；全局快捷键弹**桌宠的输入气泡**（不是主窗口）；拖文件与图片到桌宠身上；抱起桌宠拖到某个窗口上。**这四个就是 agent 的全部输入面，没有第五个**；用户输入的指令与投放的材料同口，见上。

**砍掉**：剪贴板监听——「打开应用时检测剪贴板」价值低且有点惊悚，用户没让你看，你看了。

**余力项，按代价从低到高**：

1. **读系统日历。** 不是 ICS 导入——用户已经把 Google、Exchange、订阅日历挂在系统日历里，读它一处等于同时接上所有服务，不用为每家做 OAuth。授权是一次系统弹窗，`external_id` 用事件 UID。ICS 导入退成它的兜底。
2. **语音**：录音 + 一次转写调用，转出文字后走同一条管道。
3. **手机端**：做成**极简网页，不做原生 App**。局域网加二维码配对已经定过，网页只要文字框和图片上传。原生 App 在剩下的时间里不可能。
4. **邮件 IMAP**：最贵，且要处理「读哪些邮件」这个感受问题。

手机端即使不做，「微信怎么办」也有答案：微信有桌面版，把桌宠抱过去。这个动作比手机上点分享菜单更直观，而且是我们独有的。

### 教务与日历同步

**启动时拉一次，之后每 6 小时一次，外加设置页手动按钮。** 定时读系统通知是监控用户行为；定时拉教务系统是从**用户明确授权的数据源**同步他自己的数据，采集原则原文就允许。课表与考试变化很慢，6 小时绰绰有余。

**失败不重试。** 下一个周期自然会再试，写重试循环只会把一个明确的失败变成一串看不见的失败。失败的可见性在设置页：`上次同步 09:12 · 失败：登录被拒`。**桌宠不为后台同步失败弹东西。**

**去重靠 `external_id`，不走语义链路。** 结构化来源自带稳定标识（课程号加上课时间、考试号、日历事件 UID）。**它有自己的写入口 `store/upsertByExternalId`，完全不经过 agent 循环**——库因此有两个写入者，判定方式各不相同：一条靠模型，一条靠主键。**这条路径上没有模型判断，也不该有。** 没有这一列，同步功能第一次用就会往库里灌几十条重复的课。

批量也是理由之一：一次同步进来几十门课，逐条跑循环既慢又贵，而这些条目本来就不需要理解。

覆盖时字段有变化就**写一行 `item_history`**——教务系统里考试时间变了，和用户收到一条改期通知是同一件事，处境信号一样成立。不写这一行，「改期在这条路上也有意义」就是一句没有凭据的话。

### 失败与零条目

四种情况都会发生：截图里全是废话（零条目是正常结果）；循环撞上步数上限；模型返回不合法或工具参数反复校验不过；网络断。碎片本身已经落库，但用户扔了东西进去、界面上什么都没发生——这和「坏了」长得一模一样。

**桌宠气泡四种情况说不同的话，且都以「原文已存」结尾，都能点进「最近」：**

- 零条目：`没找到需要记的东西。原文已存。`
- 步数超限：`这条太复杂，没能处理完。原文已存。` + 重试
- 抽取失败：`没能理解这条。原文已存。` + 重试
- 网络断：`连不上模型。原文已存。` + 重试

步数超限时**已经落库的工具调用不回滚**。它们各自都是有效的写入，回滚会把用户已经看见的条目又抹掉。碎片留在「最近」标为未处理完；重试之所以安全，是因为那几条已经在库里，重跑时它们就在 context 的条目清单内，模型看得见，不会重建。

**重试是对同一条碎片再跑一次管道**，不需要用户重新扔。碎片不可变，所以重试是安全的。这是「扔了就可以忘」唯一的兑现方式——只要用户相信东西没丢，失败就只是没理解。

### 工程底座

**路由：react-router，HashRouter。** 打包后页面从 `file://` 加载，BrowserRouter 在那种情况下失效，是个改起来烦、发现得晚的坑。页面有嵌套（项目 → 某个项目 → 某条条目 → 原文与引用），且「回到来处」是刚需——从日程点开一条要回日程，从项目点开同一条要回项目。手写状态机等于重写路由且更差。

```
/now  /recent  /agenda  /projects  /projects/:id  /thoughts
/items/:id  /focus  /settings
```

**桌宠的 preload 方法因此是 `openMain(path)`**，参数是路径字符串——接口更小，B 不需要知道 C 的页面枚举。

**数据层：TanStack Query。** 这是唯一必须引入的依赖。确认掉一条待确认，日程、项目、角标三处同时要变；每页各自 `useState` 意味着每处手写一遍重取，而且一定会漏。自己写 store 等于把它重写一遍且更差。加载与错误态也由它统一，包成两个组件供五页共用。

**跨窗口更新：一条 `GET /api/events`，SSE。** server 在任何写操作后广播粗粒度的「变了」，两个窗口各连一条，收到就 `invalidateQueries()`。事件不携带内容——细粒度事件等于在 HTTP 之外再长一套数据模型，两套一定会不同步，而本机重取代价可忽略。效果是：桌宠扔进一条东西，主窗口日程里自动多一条，没有人写过同步代码。

开发时 Vite 热更新会留下断掉的 SSE 连接，要允许重连。

**循环的进行中状态是第二条流，`GET /api/runs/:id/events`，携带内容。**「事件不携带内容」这条只管实体变更：实体在库里另有真相，事件再带一份就长出第二套数据模型。一次循环的进行过程是瞬时的，库里没有它，除这条流之外没有别的来源，因此不适用那条。每一步只推工具名与参数，**不推工具结果**——气泡要的只是「在对照哪个项目」，推结果只会把碎片原文送进渲染进程。映射成人话在前端做。

**preload 面在已冻的四个方法之外新增：**

```
openMain(path)              桌宠气泡点开 → 主窗口切到该路径
onFocusSessionChanged(cb)   专注开始/结束，两个窗口同步换样子
```

全局快捷键的目标从主窗口改到桌宠气泡。

### 演示数据：两份，不是一份

**演示碎片集救不了演示。** `fixtures/` 那六条是**管道的对照集**，只证明「扔进去能理解」。而「此刻」要挑一件事得先有十几条条目，「这个项目 7 天没动」要有历史，精力那几行要有专注记录——**这些演示碎片一条都不提供。现场打开，前四页全是空的。**

所以另需**演示库的种子**：一个脚本灌进「一个用了两周的库」——四五个项目、二三十条条目（有完成有未完成）、几次专注记录、几条用户说过的话、一两条被改期过的。

**种子里的日期必须相对当前时间算，不能写死。** 写死的话今天调好明天演示就全过期，「还剩 2 天」变成「已过期 3 天」，而这正是路演当天最不该出的错。

`pnpm demo:reset` 删库、建表、灌种子，三秒回到干净状态。

种子跟着 A（同一类活，都要懂数据形状），但它**是单独一件事，不能靠「做对照集顺便就有了」**。

### 专注（本轮只做最小版）

一次专注是一个**时段**：目标（哪一件事）、时长、开始与结束。「开始」即进入。

- 时段内到达的一切都不弹出，挂在该时段上；
- 结束时两个按钮：**已完成 ｜ 下次继续**，零打字；
- 结束给一份简报，列出这段时间扔的想法。

**专注开始那一刻是自然的归类时机**——「这件属于哪个项目？」在这里问不突兀，因为用户正要开始做它。这比在采集时追问归属好得多。

**本轮只做**：计时、形象在场、结束简报与两个按钮。**往后放**：拦截、勿扰、接管干扰窗口、开始时帮用户打开工作区。

**Computer Use 代办小事本轮砍掉**——34 小时做不出可靠版本，做出来是当场翻车的魔术。

**「帮你盯着新消息」本轮不做，且它撞上一条已定的线。** 第三方应用读不到系统通知；要让它成真只有「你亲手把一个窗口交给它、它在这个时段内定时看那一个窗口」这一条路，而那是定时监控，与 [[001-fragment-immutable-item-derived-with-citations]] 一同确立的采集原则冲突。本轮不做，因此不改那条线；真要做时需要先把该原则从「不定时」收紧为「范围限定在指定窗口、时间限定在该时段、每次所见都作为碎片可查可删」。

### 模块边界与分工

**边界按文件与路由划，不按功能划。** 两个人改同一个文件是唯一真正贵的耦合；先后顺序上的等待可以靠排期化解，同一个文件上的冲突不行。

| | 范围 | 独占的文件 |
|---|---|---|
| **A**　语义层 | 项目层、六个工具、agent 循环、`buildContext`、「此刻」接口、路由与 SSE、对照集与演示种子 | `packages/server/**`，`server/sync/` 除外 |
| **B**　桌面侧 | Electron 主进程、桌宠窗口与拖拽采集、教务与日历同步、主窗口的 `/focus` 与 `/settings` 两条路由 | `packages/electron/**`、`server/sync/**`、`app/src/views/{focus,settings}/**` |
| **C**　主窗口 | 设计系统、标题栏与导航、路由表、数据层、五页与待确认浮层 | `app/src/{tokens,shell}/**`、`app/src/views/{now,recent,agenda,projects,thoughts}/**` |

三处划法值得说明理由：

- **教务与日历同步归 B**，虽然它是 server 代码。它自成一体——登录、拉取、解析，唯一出口是 `store.upsertByExternalId`。B 只新增 `server/sync/` 一个目录，不改 A 的任何现有文件。
- **`/focus` 与 `/settings` 归 B**，虽然它们在主窗口里。这两条路由不复用五页的版式（专注本就整窗换一副样子），只用设计 token 与路由表；C 那边只剩「点开始 → `navigate('/focus')`」一行。设置页装着教务凭据与同步状态，与 B 手上的同步同源。
- **`store/` 与 `routes/` 归 A**，不跟着桌宠走。它们的改动全部跟着契约走，与 pipeline 同源，拆给两个人只会来回对齐。

**剩下的依赖只有三条，全部靠排序化解，没有一条需要两个人同时在场：**

1. **A 的种子与路由 → C 与 B 的一切取数。** 因此 **A 的前三步必须是项目层 → 演示种子 → 路由扩展**，在此之前不碰循环。这三步做完，server 就在用真实形状返回真实数据，C 与 B 从此不再等 A。**演示种子点名给 A**，不挂在「谁手上空谁接」下——那样的活没有人接。
2. **C 的 token 与主窗口框架 → B 的两条路由。** B 的头两件活（探针、桌宠窗口）完全不碰主窗口，等 B 转过来时框架已经在了。
3. **A 的工具调用流 → B 气泡的「进行中」。** 这条可降级：没有流时气泡显示单一的「在看…」，流接上之后才播对象。B 不为它停工。

**唯一跨人的文件是路由表与 token 文件**，各自只在一处新增一行，冲突是分钟级的。

**量的现状要摆明：三份各约 19 小时，而冻结前的可用工时不到这个数。** 砍表因此不是保险，是计划的一部分——见本文件末尾。

### Verification

| 检查 | 判断依据来自哪里 |
|---|---|
| 窗口命中与单窗口截图探针：拖到某个窗口上，截出的图内容与该窗口屏幕上的实际内容一致，且不含其他窗口 | 外部可观察事实（屏幕当下的样子），一次性探针 |
| 合并对照：「数据结构作业／数据结构考试」不合并，「组会材料／组会 PPT」合并，「高数期中 10/15 → 10/22」判为改期 | 三个记录在案的具体误判，来自真实例子 |
| context 在切了时间窗时必然含有范围说明行（起止、窗内条数、窗外条数） | 本次识别的失败：模型不知道自己没看见什么，会新建重复条目且不会想到去检索 |
| 循环撞上 8 步上限时接口返回失败，不返回成功；已落库的写入保留 | 不变量：大声失败，且已生效的写入不回滚 |
| `createItem` 的参数校验不过时，错误作为工具结果返回并允许模型重试，整次调用不作废 | 不变量：一个字段引错不该毁掉整批产出 |
| 同一条碎片重跑管道，不产生重复条目 | 不变量：重试安全，因为已落库的条目在 context 的条目清单内 |
| 项目归属与「更小的一步」的 `quote` 逐字出现在原文或所引条目里 | 不变量：判断必须指得出出处，与既有的引用逐字校验同一段代码 |
| `progress` 类条目必须挂在某个 project 上 | 不变量：进度是长期事情的记录，不存在无所属的进度 |
| 同一份课表连拉两次，`items` 不增加 | 不变量：结构化来源按 `external_id` 覆盖，不走语义链路 |
| 同一 `external_id` 的考试时间变了，覆盖时写出一行 `item_history` | 不变量：改期是处境信号，无论它来自通知还是来自同步 |
| 模型输出 `{kind:'new'}` 而同名项目已存在时，落库结果是归入既有项目，不新建 | 不变量：项目名唯一；对应「同步落地第一天出现成对重复项」这个已识别的失败 |
| 移到工具参数后 `z.toJSONSchema` 产物仍满足严格模式 | OpenAI 结构化输出严格模式的规格，机器可验 |
| 六条演示碎片过管道，结果与手写期望值逐条比对 | 用户手写的期望值 |
| `packages/app/src` 中除 tokens 文件外不出现十六进制颜色、圆角像素值、动效时长字面量 | 本次确立的规则：数值单一来源 |
| 界面每一条面向用户的文案通过风格清单 | 用户明确指定的文案风格 |
| 五页在空库状态下各有明确的空态文案，无空白页 | 不变量：用户看到的每个状态都必须是被设计过的 |

前两轮已有的静态断言继续生效：`pipeline/` 中无裸 `Date.now()`／`new Date()`、`packages/server` 中无 `electron` 引用、引用逐字可验、`fragments` 只增不改。

**Keepers**

- 合并的三条对照——对应三个记录在案的具体误判。
- 循环步数上限与「已落库不回滚」两条断言——对应「一次演示卡在原地」与「回滚抹掉用户已看见的条目」两个已识别的失败。
- context 范围说明行的断言——对应「模型不知道自己没看见什么」这个已识别的失败。
- `external_id` 幂等断言——对应「同步一次就毁库」这个已识别的失败。
- 引用可验断言（扩展到项目归属）——对应模型会凭氛围归类这个已识别风险。
- 设计 token 单一来源的静态断言——多人并行时最容易被违反的一条。
- `progress` 必须挂 project 的断言。
- 既有的四条静态断言与 README 里的两个环境坑（`ELECTRON_RUN_AS_NODE`、5123 端口占用）。

**Throwaways**

- 窗口命中探针脚本：验证完即删。
- 为看排版手塞进库的假条目：已在库外，不进仓库。

## Plan

三条并行的线，各自按序。跨线的三条依赖已在上一节标出，都落在各线的前段。

**A —— 语义层**

1. **项目层落库**：`projects` 表、`items.project_id` 与 `external_id`、进度挂载点、`progress` 必须挂项目的断言。
2. **对照集与演示种子**：六条碎片加手写期望值接 `check:fixtures`；`pnpm demo:reset` 与相对日期算出的种子数据。
3. **路由扩展**：项目增删改查、五页各自的取数、待确认队列、`GET /api/events` 的 SSE 广播、`GET /api/runs/:id/events` 的事件形状（先给空实现）。**做完这一步，C 与 B 不再等 A。前三步之前不碰循环。**
4. **工具面**：六个工具的参数 schema 与实现。抽取的 zod schema 移到 `createItem` 参数上并加项目归属三选一带 `quote`；逐字校验改为工具内执行，失败作为工具结果返回；重跑严格模式断言。`MergePlan` 与 `applyPlans` 一并删除，不留兼容路径。
5. **agent 循环**：context 组装（恒定部分、条目清单、时间窗与范围说明行）、循环驱动与 8 步上限、失败语义与已落库不回滚、拿不准以 `needs_confirm` 落库、工具调用流填上实现。补齐三条合并对照与「重跑不产生重复」的断言。
6. **`buildContext`**：四组来源分节，各带来源标签；精力只给事实。
7. **「此刻」接口**：主推 + 备选一次返回，`basis` 与 `energy_reading` 字段，落库缓存与三条失效规则。文案风格约束写进 prompt。

**B —— 桌面侧**

1. **探针**：跨平台窗口列表模块能否给出叠放顺序与边界；按窗口 ID 截图；macOS 屏幕录制授权在未打包的 Electron 下能否拿到。失败则「拖桌宠到窗口上」当场作废，立即报告，不静默降级。
2. **桌宠窗口**：多入口构建、透明置顶、手动拖动、形象接入、状态机与动效、气泡与其上的否定入口。气泡两行形态（一句话 + 动作痕迹，可点进「最近」）；接工具调用流，把工具名与参数本地映射成「在对照机器学习」一类的短句，流未就绪时退回单一的「在看…」。
3. **拖桌宠到窗口采集**：命中判定 → 单窗口截图 → 碎片入库 → 走循环，全链路。
4. **教务与日历同步**：登录、课表、考试、校历，照抄既有 Flutter/Dart 实现；`external_id` 覆盖路径与字段变化时的 `item_history`；6 小时定时与手动按钮；替换占位校历。
5. **设置页** `/settings`：模型配置、教务凭据、chronotype 两问、同步状态与上次结果。
6. **专注最小版** `/focus`：计时、形象在场、两个按钮、结束简报。

**C —— 主窗口**

1. **设计 token**（最先）：颜色（暖强调色，深浅两套）、圆角、间距、字号行高、动效三档与缓动曲线，集中一个文件，同时加静态断言。

3. **此刻页**。
4. **最近页**：投放与其产出，含零条目与三种失败的话术。
5. **日程页**：按天的轴，课表压成细带。
6. **项目页**：项目卡、未归类组、「多久没动」。
